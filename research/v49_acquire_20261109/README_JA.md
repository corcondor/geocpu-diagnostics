# v49 外部データ6種の取得・検査パイプライン

Hugging Face の公開データ6種を、**Google Colab の CPU ランタイム**で Google Drive に取得し、検査して、GeoCPU の学習用の行（JSONL）に直します。
パソコンには何も取ってきません。GPU も使いません。パスワード・API キー・トークンも要りません（6つとも公開・承認不要のリポジトリです）。

## Colab での開き方

次の URL を開くと、GitHub 上のノートブックが Colab で開きます。ブランチ名に `/` が入っているので、Colab の URL では `/` を `%2F` に直した **1つ目** がたぶん開けます（2つ目は `/` のままの形で、開けないことが多い）。

https://colab.research.google.com/github/corcondor/geocpu-diagnostics/blob/research%2Fv49-acquire-20261109/research/v49_acquire_20261109/colab_acquire_check.ipynb

https://colab.research.google.com/github/corcondor/geocpu-diagnostics/blob/research/v49-acquire-20261109/research/v49_acquire_20261109/colab_acquire_check.ipynb

ブランチ名の `/` に左右されない形は、コミットで指す形です: `https://colab.research.google.com/github/corcondor/geocpu-diagnostics/blob/<コミットのsha>/research/v49_acquire_20261109/colab_acquire_check.ipynb`。`<コミットのsha>` は **この修正を push したコミットの40桁の sha** に置き換えてください（修正前のコミットの sha を使うと、修正前のノートブックが開きます）。リポジトリが非公開なら、Colab で GitHub にサインインする必要があります。URL を push 前に試すことはできていません（このパソコンからは通信していないため）。

どれも開けないとき（ブランチをまだ push していない場合など）は、`colab_acquire_check.ipynb` を手元に置いて、Colab の「ファイル > ノートブックをアップロード」（File > Upload notebook）で開きます。ノートブックは自分の中に4つのコードを抱えているので、これ1つで動きます。大きさは約1.09 MB です（4つのコードと、v48 の評価セット4種を中に持つため）。大きさの上限（`test_make_notebook.py`）は、1.1 MB から **1.2 MB に意図して引き上げました**（今回の修正で増えた分があり、余裕が8 KB しかなかったため）。埋め込んだコードからコメントを削って小さくすることは、していません。テストは「埋め込んだ4つのコードが、ファイルと1文字も違わない」ことを確かめ、3b は「読み込んだ中身が埋め込みと同じ」ことを確かめます。埋め込みだけコメントを削ると、この2つの照合が成り立たなくなります。ファイル自体のコメントには、各規則を決めた理由が書いてあるので、そちらも削っていません。

## あなたが押すもの（クリックの全部）

パスワード・API キー・トークンも要りません。押すのは次のものだけです。

1. **「このまま実行」**: GitHub から開いたノートブックを最初に実行するとき、「このノートブックは Google が作成したものではありません」の確認が出ます（英語の画面では "Run anyway"）。最初の1回だけです。ファイルをアップロードして開く方法（File > Upload notebook）でも、同じ確認が出ることがあります。
2. **ランタイムのタイプ**: 「ランタイム → ランタイムのタイプを変更」で、ハードウェア アクセラレータが **なし（CPU）** になっていることを確かめます。GPU が付いたままだとセル3a が止まります（有料の計算資源を使わないため）。
3. **「ランタイム → すべてのセルを実行」**。
4. **Drive のアクセス許可**（セル3a の `drive.mount`）: アカウントを選んで「許可」（画面が2〜3枚出ます）。
5. **Drive のつなぎ直しのたびの許可（出るかどうかは未確認）**: この処理は Drive を外してつなぎ直すので（データセットごとの取得のあと、変換の波ごと、書き込みの多いステップのあと、最後の終了。全体で約20回以上）、許可の画面がそのたびに出るかもしれません。出るかどうかは本物の Colab でしか確かめられないので、セル3c の予行演習（何も書かず、数回つなぎ直すだけ）で **先に** 試します。もう一度出たなら、本番でも同じ回数（セル3c が「約N回」と表示します）出るので、そのたびに「許可」を押します（押さないとそのセルは待ち続けます）。出ないなら、あとは放っておけます。
6. **止まったとき**（接続が切れた・約12時間たった・`FAIL` が出た）: 接続が切れたときは画面の **「再接続」**（Reconnect）を押し、新しいランタイムで始め直します。メッセージの指示を直してから、もう一度「すべてのセルを実行」。取得済みのファイルは検証して飛ばし、変換済みの行・シャードは Drive から戻し、終わった 7a・6c は保存した結果を使うので、続きから動きます。セル2が「セッションを再起動」を求めたときだけ、「ランタイム → セッションを再起動」してからやり直します。
7. **タブを開いたまま**: 7b は長くかかるので、ブラウザのタブを閉じないでください（閉じると実行中のセルが止まることがあります）。止まっても、できたシャード・データセットは Drive にあります。
8. 設定を変えるとき（`RUN_SUFFIX`・`RAW_SUFFIX`・`ONLY` など）だけ、セル3a の上のほうの値を書き換えます。それ以外のセルを編集する必要はありません（本体のコードは折りたたんだセル3b にあり、編集しません）。

## 実行の手順

1. 上の「あなたが押すもの」の 1〜4 をします。
2. 3c（Drive の予行演習）と 3d（サンドボックスの自己診断）が、データを取る前に通ります。3d は coding を処理するときだけ動き、通らないと止まります（Linux で初めて動かすコードなので、ここで外れる可能性が一番高い）。
3. 各セルの最後に `PASS` か `FAIL` が出ます。`FAIL` のときはそこで止まります。メッセージの内容を直してから、もう一度「すべてのセルを実行」します。
4. 7a（最初の2,000件だけの試運転）の最後に、全体の所要時間の目安が出ます。これは見積もりで、実測ではありません。コードの実行検証（coding）が一番長くなります。7a は一度終わると結果を保存し、再実行では測り直しません（測り直すと数字が変わって、上書き拒否で止まっていました）。
5. 7b は長くかかります（見積もりは全体で3.5〜6.5時間。実測ではありません）。実行中のセルを自分で止めたときは、動いている変換プロセスも一緒に止まります。
6. 最後のセル10に `REPORT_JA.md` の全文が出ます。

一部のデータセットだけ試すとき: セル3a の `ONLY` を `("jaquad", "toolace")` のようにします。試運転は自分用の出力フォルダ（`v49_acquire_20261109_only_jaquad-toolace`）に書くので、あとの本番（`ONLY = None`）と同じ `RUN_SUFFIX` でぶつかりません。変換済みの行・最終の行は共有されます。

Colab 側の目安: メモリ 12GB、ディスク約100GB のうち、この処理はローカルに約4GB（取得したファイルの写し＋変換結果）を使います。Drive には元ファイル約1.9GB に加えて、変換済みの行と最終の行が入ります（7a が見積もりを出し、足りなければ 7b の前に止まります）。

## どこに何が書かれるか

すべて `GeoCPU_v47_fullmodel_20261106/` の下の**新しいフォルダ**です。既にあるファイルを上書きも削除もしません。同じ名前で内容の違うファイルが既にあれば、そこで止まります。書き込みはまず `<名前>.part` に書いて、行き先がまだ無いことを確かめてから名前を付け替えるので、実行が途中で止まっても欠けたファイルは残りません（残った `.part` は `.part.stale-N` に退避するだけで、消しません）。

```
external_data_v49/                          取得した元ファイル（RAW_SUFFIX で別のフォルダにできる）
  <リポジトリ名の / を __ にしたもの>/
    README.md                               データカード（ライセンスの文言はここ）
    <リポジトリ内のパス>                     train のファイルだけ
    commit_pin.json                         取得するコミット（最初のファイルより前に書く。再実行はこのコミットを取る）
    provenance.json / PROVENANCE.md         コミット・sha256・ライセンス・帰属表示の記録（ファイルが Drive に着いたあとに書く）
  do_not_train_dev/…                        JaQuAD の dev（照合専用。学習には使わない）
  do_not_train_validation/…                 HotpotQA の validation（照合専用）
external_data_v49_stageA[<RAW_SUFFIX>]/<変換器タグ>/<データセット>/   絞り込み前の変換結果（再開用。RUN_SUFFIX には左右されない。RAW_SUFFIX を変えると別のフォルダ）
  <データセット>__shards/<範囲>/             coding・tengentoppa の小分け（シャード）
external_data_v49_rows/<データセット>/       最終の行（採用候補: coding, tengentoppa, jaquad, hotpot）
  train.jsonl  dev.jsonl  heldout.jsonl  manifest.json  ATTRIBUTION.md  LICENSE_NOTICE.txt  [LICENSE-Apache-2.0.txt]
external_data_v49_rows/_HOLD_do_not_mix/<データセット>/   保留（toolace, wizard）。DO_NOT_TRAIN_UNTIL_APPROVED.txt つき。学習に混ぜない
v49_acquire_20261109[<RUN_SUFFIX>][_only_<データセット>]/     ONLY の試運転は `_only_...` が付いた自分用のフォルダ
  registry.json                             機械が読む記録（データセットごとの長さの情報 mean_len・mean_masked・length_hist・supervised_chars_by_split を含む）
  REPORT_JA.md                              人が読む報告（日本語の表）
  reading/raw_<データセット>_100.txt        元データの100行（目視用）
  reading/final_<データセット>_100.txt      最終の行の100行（目視用）
  filters/<データセット>_dropped.tsv        落とした行の一覧（行番号・id・理由）
  filters/semantic_review_<ハッシュ>.txt    評価問題に似た行の目視用リスト（8b）
  state/*.json                              各セルの結果（再開用）、vocab_cache.json
  run_info_<日時>_<pid>_<n>.json            実行環境と各セルの所要時間
```

変換済みの行（`external_data_v49_stageA/`）は、変換のコード（convert.py・サンドボックス・記号の正規化・語彙）と変換の設定（長さの上限・python の方針・Python の版）と **元データ（コミットと train ファイルの sha256）** が同じなら使い回されます。元データが違うと、使い回さずに止まります。絞り込み側（pipeline.py、checks.py の重複・照合の部分）を直したり、`RUN_SUFFIX` を変えたりしても、数時間かかる変換はやり直しません。

registry.json の長さの情報（学習計画が読む）: `mean_len` = 最終の train 行の len(prompt + target) + 1（EOS 1つ分）の平均、`mean_masked` = 損失から外す文字（ツール出力）の平均、`length_hist` = 64文字刻みの train 行数（キーは区間の中央値＝下端+32）、`supervised_chars_by_split` = 分割ごと（train / dev / heldout）の教師あり文字数。manifest.json にも同じ値があります。

データセット名（フォルダ名）: `coding`（llm-jp/Synthetic-JP-EN-Coding-Dataset）、`tengentoppa`（DeL-TaiseiOzaki/Tengentoppa-sft-qwen2.5-32b-reasoning-100k）、`jaquad`（SkelterLabsInc/JaQuAD）、`hotpot`（hotpotqa/hotpot_qa、distractor）、`toolace`（Team-ACE/ToolACE）、`wizard`（llm-jp/wizardlm8x22b-logical-math-coding-sft-ja）。

行の形は既存のファミリーと同じです（`id, source, license, split, training_category, family, structural_template, difficulty, _v46_group, prompt, target, full_text, loss_mask_spans, tool_steps, reference_final_answer, answer_type`。加えて `attribution` と `adoption`）。`full_text` は `prompt + target` と完全に同じで、`len(full_text)+1` は 2,048 以下（実際は 1,900 文字以内）です。ツールの出力（Python の実行結果、関数の結果）は `loss_mask_spans` と `tool_steps` で損失から外してあります。

### 分割（heldout 3%・dev 1%・train 96%）の単位

分割の単位はデータセットごとに違います。**dev / heldout が学習行から独立しているのは、JaQuAD と HotpotQA の2つだけです。**

- **jaquad**: 記事（タイトル）単位。同じ記事の質問は同じ分割に入ります。
- **hotpot**: 根拠の段落が共通する質問を1つに繋いだ連結成分（全 train レコードに対する union-find）単位。根拠の段落を共有する質問は同じ分割に入ります。
- **coding・tengentoppa・toolace・wizard**: 行単位です。これらは機械が作った文で自然なグループがないので、同じ種から作られた兄弟（Evol-Instruct の連鎖など）が train と dev / heldout にまたがって入りえます。8 で、学習行と推定 Jaccard 0.5 以上で似ている dev / heldout の行は落としますが、言い換えレベルの兄弟は残ります。そのため、これら4つの dev / heldout は**グループ独立の評価として使わないでください**（形式の確認用です）。manifest・registry・REPORT_JA.md のどれにも `split_unit` と `group_independent_dev_heldout` が書いてあります。

## REPORT_JA.md の読み方

- **1. 結果の一覧**: データセットごとに、元の件数 → 変換後 → 完全重複除去後 → 近似重複除去後 → 評価データ除外後 → 旧コーパス重複除去後 → dev/heldout の近い兄弟除去後（これが採用候補の行数）。各段階は前の段階に残った行だけを対象にした順番の絞り込みです。教師あり文字数は、`target` から損失に入らない部分（ツールの出力）を引いた文字数です。
- **採用判定は暫定の提案**です。事前に決めた件数はなく、検査の結果から出ます。種類は次のとおりです。
  - 採用候補: 人手で作られたデータ（jaquad、hotpot）と、coding。coding の python 行は、**実行して、答え自身の保存出力と一致したものだけ**が入ります（それが「検証済み」の python 行で、報告の数字はこれだけです）。保存出力が無くて実行しかできなかった行は、数だけ記録して残しません。他言語の code_text 行は実行しておらず、未検証です。
  - 条件付き候補: tengentoppa（Qwen2.5-32B が作り、人手の確認がない）。
  - 保留: wizard（計画の「数学の明らかな誤りがあるものは避ける」に該当）。測れた算術式の誤り率は書きますが、自動では採用候補に上げません。誤り率が小さくても、100行を読んで、あなたが決めます。
  - 保留: toolace（生成モデルがカードにも論文にも書かれていないため、確認できるまで保留）。
  - 不採用: 採用できる行が0件のとき。

## サンドボックス（データ中のコードを実行する仕組み）の正直な説明

coding の python 行は、データ中のコード（LLM が書いたもの）を実行して、保存された出力を実行結果で置き換えます。

- このサンドボックスは、**モデル自身の実行器の規則をすべて掛けたうえで、さらに厳しい規則を足しています**（`checks.static_check(profile="executor")`。足してあるのは、下で説明する名前の許可リスト・モジュールの別名の規則・文字列の型注釈の拒否・呼び出しのキーワードの規則・検査そのものの上限です）。そのため、**モデルの実行器なら受け付けるコードでも、ここでは捨てる行があります**（収量が減るだけで、安全の問題ではありません）。使える import は math・cmath・decimal・fractions・statistics・itertools・functools・operator・collections だけで、クラス定義、属性への代入、アンダースコアで始まる属性、`open`・`eval`・`exec`・`getattr`、`import re` / `json` / `random` などは使えません。実行器が受け付けないコードを、「成功した観測」の行にして学習させることはありません。以前の広い規則（`wide`）は廃止しました。
- さらに、レビューで見つかった抜け道（`from operator import attrgetter, methodcaller`、組み立てた文字列の `.format`、ジェネレータのフレーム、`random._os` のようなモジュール経由の到達、`match` 文のクラスパターンが属性名を文字列で運ぶ `case int(__class__=c)`）を静的に拒否し、モジュールは「公開された、モジュール以外の属性」だけの名前空間で渡します。`match` 文のクラスパターンは **拒否が既定**です: キーワード属性（`case str(format=f)`、`case int(real=r)` など、名前は何でも）を持つクラスパターンは全部拒否し、クラスパターンに書けるのは組み込みの型名（int・float・str・bool・list・tuple・dict・set・frozenset・complex・bytes）だけで、その名前をコード内で別の値に束縛し直しているときも拒否します（位置引数だけの `case int(n):` は、対象そのものに一致するだけで属性を1つも読まないので動きます）。以前は禁止する属性名を1つずつ足していて（`__class__`、次に `format`）、`case str(format=f)` が実行時に組み立てた文字列の `.format` を取り出せました。`from m import n` の名前にも、属性と同じ規則（`format` / `format_map` を含む）を掛けます。as パターンなどの束縛名・`except ... as`・`import ... as`・関数名・引数名は、名前を束縛するだけで属性を読まないので、名前の規則（アンダースコア2つで始まる名前と禁止名）だけです。
- **呼び出しのキーワード**（`f(name=v)` の `name`）は、辞書のキーではなく、**呼ばれる関数の引数の名前に結びつきます**。非公開の引数にも届きます（`Fraction(4, 8, _normalize=False)` は Python 3.10 / 3.11 で約分されない分数を作ります）。そこで、**アンダースコアで始まるキーワードは全部拒否します**（`static:name:_normalize`）。それ以外（`dict(format=1)`、`sorted(key=...)`、`print(sep=...)`、`round(x, ndigits=1)`、`Context(prec=3)`、`deque(maxlen=2)`、`partial(int, base=2)` など）は今までどおり通ります。**残る限界**: `f(**{'_normalize': False})` のように、`**` で渡す辞書のキーは実行時に決まるので、静的な検査には見えません（拒否できません）。この場合は、静的な層も実行時の層も止めません（Python 3.10 / 3.11 では実際に実行され、約分されない分数 4/8 ができるだけで、それ以外の力は得ません）。`**` を呼び出しで全部拒否すれば塞げますが、収量が少し減るので、あなたが決めてください（今は拒否していません）。
- **検査そのものの上限（1行で変換が止まらないように）**。以前は、3 KB の属性の連鎖 `math.pi.pi.pi…`（1,100段）や、1,100段に入れ子にした書式指定 `'{:{:{:…}}}'.format(1)` を1行入れるだけで、検査器から `RecursionError` が**例外として**出ました。`convert.Checks._sandbox` は検査器の例外を「サンドボックスの故障」と見なして変換全体を止めます。**実際に止まるかは、変換を呼んだ側のスタックの深さしだいです**（測った結果。Python 3.12・旧版の検査器）: スタックが浅いと、行の長さの上限（1,900文字、連鎖で約570段）のせいで、止まるほど長い連鎖はそもそもサンドボックスまで届きません（連鎖940〜988段は `row_too_long` で除外、992段以上は1回目の静的な検査の `exception:RecursionError` という**別のカテゴリの除外**になるだけでした）。スタックに520段が積まれた状態では、**1,453バイト・470段の連鎖1行が `SandboxUnavailable` で変換を止めました**（1回目の検査は通り、2回目＝サンドボックスの中の検査で溢れたため）。Colab の呼び出しの深さは、ここでは測れていません。990段の連鎖は、例外にはなりませんが、段数の2乗の時間（手元で約0.4秒）がかかりました。いまは次のとおりです。(1) 構文木の深さが **200段** を超えるコード、(2) 書式指定の入れ子が **8段** を超えるコード、(3) 検査の途中でスタックやメモリが尽きたコード、(4) 構文解析そのものが `RecursionError` / `MemoryError` / `ValueError` などを出したコードは、**例外ではなく行の除外**になります（カテゴリは `static:too_deep`、書式指定は `static:format_string`、構文解析が読めないものは `static:syntax`）。検査は構文解析の直後、どの走査よりも前に深さを測り（再帰せず、明示のスタックで測ります）、モジュール名の連鎖の解決も繰り返しとメモで、段数に比例する時間で終わります（3 KB の連鎖は0.02秒以下）。**収量への影響**: `a + b + c + …` のように左に伸びる式や `elif` の梯子は、1項・1枝につき1段なので、およそ200項・200枝を超えると除外になります（数学の解答コードにはまず出ない大きさです。100枝の `elif` と150項の和は通ることをテストで確かめています）。検査の規則（この上限を含む）を変えると、変換の「コードの版」の指紋（`pipeline.py` の `converter_hashes` の `checks.sandbox_and_normaliser`）が変わるので、古い規則で変換して保存した結果があっても使われず、やり直しになります（意図した動きです。今回の修正もこの指紋を変えます）。
- **使える名前は、モジュールごとの固定の許可リストだけです（拒否が既定。`checks.MODULE_NAMES`）。** 以前は「危ない名前を禁止するリスト」で、リストにない抜け道が2つ見つかりました。`functools.update_wrapper` / `wraps` は、コピーする属性の名前を文字列（`assigned=('__code__',)`）で受け取り、モジュールの内側で `setattr` / `getattr` を呼ぶので、属性名が静的な検査に見えないままオブジェクトに届きます。`functools.singledispatch(...).register()` は、文字列の型注釈を式として評価します（`typing.get_type_hints`）。そこで次の2つの層で、リストにない名前を使えなくしました。

## 評価データとの照合（8）: 英語の断片の扱い（2026-11-10 の変更）

**何が起きたか**: 本物の Colab で測ったところ、8 の評価データ照合が HotpotQA の 78,864 行のうち 76,288 行（全体では 236,957 行のうち 106,224 行）を落としました。原因は断片の長さです。評価文は、数字と空白を除いて、13文字の断片にして索引にします。日本語なら13文字はおよそ一文ですが、英語は空白が消えるので13文字は2〜3語にしかなりません。たとえば `smagazinepubl`（woman's magazine published）や `thmilitarypol`（th military police）のようなありふれた言い回しが、HotpotQA の validation の質問（索引に入るのは質問だけ）と、passage の側で偶然に一致していました。どの行も、評価の質問を写したものではありません（`EvalIndex.find_sources` で、一致した断片がどの質問の中にあるかを確かめました）。

**何を変えたか**（`checks.py` の `EvalIndex` と `decontaminate` だけです）:

- 13文字がすべて ASCII（英字・記号）の断片は、**それだけでは行を除外しません**。同じ1つの評価文の中で、ASCII の断片が途切れずに連続して一致し、正規化後の文字数で **40文字以上（連続28個の断片）** になったときだけ数えます（`ASCII_RUN_CHARS = 40`）。別々の評価文にまたがる連続は数えません。
- ASCII でない文字を1つでも含む断片（日本語など）は、**これまでと完全に同じ**です（13文字・評価問題20件以上が共有する定型句は数えない）。日本語の前置きに英語の passage が付いた行は、断片ごとに判定します。日本語の13文字の写しがあれば除外し、英語の偶然の一致だけでは除外しません。
- **変えていないもの**: 40文字以上の評価文が丸ごと入っている行の除外（丸ごと一致）、評価問題20件以上が共有する断片を定型句として数えない規則、結果が毎回同じこと、正規化（数字と空白を除く）、変換のコード（`_VALIDATE_SRC` など）。変換の指紋 `checks.sandbox_and_normaliser` は変わらないので、Drive に保存済みの変換済みの行（`external_data_v49_stageA/<指紋>/`）はそのまま再利用されます。

**限界（わかっていること）**:

- **英語の評価文が正規化後に40文字より短いとき、そのまま写した行も、断片では見つかりません**（丸ごと一致も40文字以上が条件です）。以前は見つかりました。たとえば `The old library closed early today.`（正規化後30文字）を写した行は、今は除外されません。テストで確かめてあります。
- 英語の写しは、**40文字続けて同じ**ときだけ見つかります。言い換えや翻訳は、以前から見つかりません。
- 数字は正規化で消えるので、**数字だけの評価文は索引に入りません**（13桁の数字が偶然一致しても、40桁の数字が一致しても、数字だけでは何も起きません。変更の前も後も同じです）。文字が混じっていれば、数字を除いた文字が40文字続くときに見つかります。
- 日本語の評価文の中の**短い ASCII の部分（関数名・コードの一行）だけ**が一致した行は、除外されなくなりました。手元の本物の評価ファイルで、評価文を部分的に写した変形を60行ずつ試したところ、T1（SWE の step control）の3種の変形で4/60、v42 の「後半だけ」の変形で11/60 が、以前は `heapq.heappop` や `R0 += 0` のような短い ASCII の断片だけで除外されていました。評価文を丸ごと写した行、日本語13文字以上の写し、数字だけを変えた写しは、すべて今までどおり除外されます（60/60、v48 の4セットは128/128）。

**報告で見るところ**（`registry.json` の `decontam` と、REPORT_JA.md の2）: `rows_flagged_ascii_run`（40文字以上の ASCII の連続一致で除外した行）、`rows_not_flagged_ascii_short`（旧規則なら除外だったが今回は残した行。短い ASCII の断片にしか一致していません）、それぞれのデータセット別（`_by_dataset`）、`rows_flagged_legacy_13gram`（旧規則での除外数）、`ascii_short_top` と `ascii_short_examples`（残した行がよく一致した短い断片と、その断片がある評価文の例）。`rows_flagged_ascii_run` は、定型句でない ASCII の連続一致（40文字以上）を1つでも含んで除外された行の数です。`rows_flagged - rows_flagged_ascii_run` は、それを含まずに除外された行（日本語の13文字一致、または丸ごと一致だけで除外された行）です。

**測定**（手元の合成データ。本物の HotpotQA ではありません）: validation の質問に似せた 7,002 問と、2段落（約3,000文字）の行を使い、質問と passage は文の型を変えて、語彙だけを共有させました。旧規則では 300/300 行（100%）が除外され、新規則では 0/300 行（0%）です（`test_checks.py` の `TestAsciiRunDecontaminate` が、この前後の割合を毎回表示します）。20万行（1行約120文字）を処理する時間は、旧規則と同じ程度です（テストの出力に出ます）。
